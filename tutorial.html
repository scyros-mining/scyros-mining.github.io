Tutorial

This tutorial runs a complete small study with Scyros, from sampling GitHub to a table of functions that you can analyse. You do not need to write any code. You type nine short commands in a terminal, and check the result of each one before you go on.

The study answers one question: which Java and Go functions use concurrency, and what do they look like? Once you have run it, you can change a single file to ask your own question.

Before you start

You need three things.

A terminal

On macOS, open Terminal. On Windows, open PowerShell. On Linux, open your usual terminal. Every command in this tutorial works the same way in all three.

Scyros

Follow the installation instructions, then check that it works: 

scyros --version

Check: the terminal prints the version, such as scyros 0.4.0. If it says that the command is not found, close the terminal, open a new one and try again: the installer updates your settings only for new terminals.

A GitHub token

Scyros asks GitHub about many repositories. GitHub answers far more requests from you if you identify yourself with a personal access token. The token only needs to read public information:

  1. On GitHub, open Settings, then Developer settings, Personal access tokens and Fine-grained tokens.
  2. Choose Generate new token, give it a name and an expiry date, and leave the repository access on public repositories. Do not add any permissions.
  3. Copy the token. GitHub shows it only once.

GitHub's own guide has screenshots of each step. Keep the token secret, like a password. You will save it in a file in step 1.

The plan

A study with Scyros is a chain of steps. Each step reads the file that the previous step wrote and writes a new one, so you can stop, look at a file and go on later. Here is the whole chain:

StepWhat it doesWrites
1Create a folder for the studytokens.csv
2Describe what you are looking forconcurrency.json
3Pick 2,000 repositories at randomids.csv
4Remove repositories counted twice, and forksunique_ids.csv, repos.csv
5Ask GitHub about each repository and keep the substantial onesmetadata.csv, filtered.csv
6Keep the repositories that contain Java or Golanguages.csv, selected.csv
7Download their code and keep the files that use concurrencyrepos/, files.csv, projects.csv
8Remove duplicate filesunique_files.csv, duplicates.csv
9Extract the functions that use concurrencyfunctions.csv, function_logs.csv

The study sends about 1,500 requests to GitHub, mostly in step 5, which asks about each repository in turn. That is well within the 5,000 requests per hour that a token allows. Most of the time is spent waiting for GitHub, and long steps show a progress bar.

The steps

1. Create a folder for the study

Create a folder and move into it:

mkdir concurrency-study
cd concurrency-study

In this folder, create a file called tokens.csv with a text editor. Its first line is the word token, and its second line is the token you copied from GitHub:

Save it as plain text. In TextEdit on macOS, first choose Format, then Make Plain Text. In Notepad on Windows, make sure the name does not end in .txt.

Check: ls lists tokens.csv. On Windows, the command ls works in PowerShell too.

2. Describe what you are looking for

A keyword file tells Scyros which languages to keep, which files belong to each language, and which words to search for. Create concurrency.json in the same folder, with this content:

Here is what each part means:

  • "name" is the language as GitHub calls it, in lower case. Scyros uses it to find repositories that contain the language, and to choose how to read its code.
  • "extensions" says which files belong to the language: files ending in .java are Java, files ending in .go are Go.
  • The "keywords" inside a language only count in files of that language. go starts a new task in Go, so it is only searched for in Go files.
  • The "keywords" list at the end counts in every language. lock and unlock are method names in both Java and Go.

A keyword matches whole words, and capital letters do not matter. Thread therefore also matches a variable called thread, but not ThreadLocal. Like any keyword search, this finds some functions that do not really use concurrency. The keyword file reference has all the rules.

Check: the file starts with { and ends with }, and every quote and comma is in place. If a later step says that it cannot parse the JSON file, compare your file with the one above.

3. Sample repositories

scyros ids -t tokens.csv -n 2000 -o ids.csv

Every repository on GitHub has a number, its id. Scyros picks random ids and records the public repositories that come right after each one, 100 per request to GitHub, until it has 2,000. This gives a random sample of GitHub, rather than only its popular projects. The result is a table with one row per repository:

fork is 1 when the repository is a copy of another one. Scyros starts from the same random ids every time you run this command, so the sample can be repeated. To draw a different sample, add -s and any number, such as -s 7.

Check: ids.csv has about 2,000 rows. You can open it in a spreadsheet program, or count its lines in the terminal. On macOS and Linux, type wc -l ids.csv. In PowerShell, type (Get-Content ids.csv).Count. The count includes the first line, which holds the column names.

4. Remove duplicates and forks

scyros duplicate_ids -i ids.csv -o unique_ids.csv
scyros forks -i unique_ids.csv -o repos.csv

Two random ids can be close enough to record the same repository twice, so the first command keeps each repository once. Forks, such as carol/spring-petclinic above, contain someone else's code. Keeping them would count that code twice, so the second command removes them.

Check: each command prints how many rows it removed. Duplicates are rare. Forks are not: in the floating-point study, about one repository in three was a fork, so expect repos.csv to hold about 1,300 repositories.

5. Collect metadata and keep substantial repositories

scyros metadata -i repos.csv -t tokens.csv -o metadata.csv

Scyros asks GitHub about each repository: its main language, its size, when it was created, and so on. This is the longest step, because it sends one request per repository. Dates are written as Unix timestamps, the number of seconds since 1 January 1970, and sizes are in kB:

Many repositories on GitHub are tiny, or were used for only a few days. The next command keeps the substantial ones: 

scyros filter_metadata -i metadata.csv -s 50 -a 60 --non-code -o filtered.csv
  • -s 50 keeps repositories of at least 50 kB. bob/dotfiles is dropped, since it is only 18 kB.
  • -a 60 keeps repositories with at least 60 days between their creation and the last time someone added code to them.
  • --non-code drops repositories in which GitHub finds no programming language, such as those that only hold documents.

These limits only describe the repository itself. Stars and forks are left out on purpose, because they would favour popular projects and bias the sample. filtered.csv has the same columns as metadata.csv, except that created and pushed are replaced by age, the number of days between them.

Check: some rows of metadata.csv have a name such as http/2 404. These repositories were deleted or made private after you sampled them, and filter_metadata drops them. Only about one repository in ten passes the filters, so expect filtered.csv to hold between 100 and 150 repositories.

6. Keep the Java and Go repositories

scyros languages -i filtered.csv -t tokens.csv -o languages.csv

GitHub gives each repository one main language, but a Kotlin app may also contain some Java. This command records every language in each repository, with how many bytes of code it has. It also records the latest commit, which identifies the exact version of the code that step 7 downloads:

Then keep the repositories that contain at least one language from your keyword file:

scyros filter_languages -i languages.csv -l concurrency.json -o selected.csv

Check: both repositories above are kept. In the floating-point study, about one repository in eight that passed step 5 contained Java or Go, mostly Java. Expect selected.csv to hold around 15 repositories. If it holds none, see If something goes wrong.

7. Download the code

scyros download -i selected.csv -t tokens.csv -k concurrency.json -d repos -p projects.csv -f files.csv

Scyros downloads each repository into the folder repos, at the commit recorded in step 6. Anyone who runs your study later therefore gets exactly the same code. It then deletes every file that is neither Java nor Go, and every file that contains none of your keywords. files.csv lists the files that remain, with the number of keyword matches in each, in a column named after your keyword file:

loc is the number of lines and words the number of words in the file. projects.csv has one row per repository, with its numbers of files, lines and words before and after the keyword filter.

Check: the folder repos contains one folder per repository, and you can open any of the files listed in files.csv in a text editor.

8. Remove duplicate files

scyros duplicate_files -i files.csv -s bow -o unique_files.csv -m duplicates.csv

The same file often appears in several repositories, for example when projects copy a library into their own code. Counting it every time would distort your results. With -s bow ("bag of words"), two files count as duplicates when they contain the same words, even in a different order or with different spacing. unique_files.csv keeps one file from each group, and adds a count column with the number of copies. duplicates.csv shows which file stands for each copy.

Check: unique_files.csv has at most as many rows as files.csv, and most files have a count of 1.

9. Extract the functions

scyros parse -i unique_files.csv -k concurrency.json -o functions.csv -l function_logs.csv

Scyros reads the code of each file, splits it into functions, and keeps the functions that contain one of your keywords. This time it skips comments and text in quotes, so a comment that mentions a lock does not count. Each function is saved in its own file, next to the file it comes from, in a folder ending in .functions. Its name gives the line and column where the function starts:

Your results

Every file that the study wrote is still in the folder:

concurrency-study/
  tokens.csv          concurrency.json
  ids.csv             unique_ids.csv       repos.csv
  metadata.csv        filtered.csv
  languages.csv       selected.csv
  projects.csv        files.csv            repos/
  unique_files.csv    duplicates.csv
  functions.csv       function_logs.csv

functions.csv is your dataset. Open it in a spreadsheet program, or in the statistics software you prefer, and look for patterns: how long are the functions that use concurrency, how often do they contain loops, and how do Java and Go compare? The reference explains every column.

Because every intermediate file is kept, you can also go back: open filtered.csv to see which repositories passed step 5, or change a filter and run only the steps after it again.

If something goes wrong

"File … already exists. Use --force to override it."
You have run this step before. To run it again, add --force at the end of the command. The commands that call GitHub (ids, metadata, languages and download) do not show this message: they continue where they stopped instead.
A step stopped halfway, for example because your computer went to sleep
Run the same command again. The commands that call GitHub continue where they stopped. The others are quick enough to run again with --force.
"scyros: command not found", or "scyros is not recognised"
Open a new terminal. If that does not help, install Scyros again following the instructions.
Errors about the token, or every repository fails
Check that tokens.csv is plain text, that its first line is exactly token, and that the token has not expired.
A step cannot parse the JSON file
Look for a missing comma, quote or bracket in concurrency.json, or copy it again from step 2.
selected.csv is empty, or very small
Random samples vary. Draw a larger one: run step 3 again with -n 5000 --force, then every later step with --force. Step 5 then sends about 3,300 requests, which is still within the hourly limit of a token.
GitHub's rate limit
If you send too many requests, Scyros waits and tries again, so the step only takes longer. Several tokens from the same account do not raise the limit.

Next steps

  • Ask your own question. Change the languages and keywords in the keyword file, and run the steps again. The keyword file reference shows how to use regular expressions, several keyword files at once, or no keywords at all to keep every function.
  • Make the study larger. Increase -n in step 3. The other commands stay the same. For large samples, spread the work over several hours or several days: every step that calls GitHub can be stopped and continued.
  • Look up an option. The docs describe every subcommand, the files it reads and writes, and its main options. scyros <subcommand> --help lists all of them.
  • Publish your study. Share your keyword file, your commands and ids.csv, so that others can repeat it, and please cite Scyros.
