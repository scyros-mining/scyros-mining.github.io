Tutorial

This tutorial runs a complete, small-scale mining study with Scyros. In this example study, we will use Scyros to collect Java and Go functions that use concurrency primitives. The tutorial follows Scyros 0.4.0.

Prerequisites

To run this tutorial you will need to have Scyros installed as well as a personal access GitHub token to communicate with the GitHub REST API.

Scyros

Install Scyros following the installation instructions, and confirm that it is on your path: 

scyros --version

scyros --help lists the available subcommands, and scyros <subcommand> --help describes all the options for a given subcommand.

GitHub token

To sample repositories, query their metadata or download them, you will need a personal access token to the GitHub REST API. In GitHub, go to Settings → Developer settings → Personal access tokens → Fine-grained tokens, generate a token with public repository access only (see GitHub's documentation for details), and copy it in a file tokens.csv of this form:

Do not commit or share this file.

Pipeline overview

Running a study with Scyros involves executing a series of commands that process data in a pipeline. Each step of the pipeline reads the CSV file written by the previous step and writes a new one, so every intermediate stage of the sample can be inspected, reported and rerun independently.

Step Purpose Output
1 Draw a random sample of 2,000 repositories ids.csv
2 Remove duplicate ids unique_ids.csv
3 Remove forks ids_without_forks.csv
4 Collect repository metadata metadata.csv
5 Exclude trivial repositories filtered_metadata.csv
6 Collect the languages and latest commit of each repository languages.csv
7 Keep repositories containing Java or Go java_go_repos.csv
8 Download source code at a fixed commit and keep matching files repos/, projects.csv, files.csv
9 Remove duplicate files unique_files.csv, duplicates.csv
10 Extract matching functions and compute their metrics functions.csv, function_logs.csv

Steps

1. Sample repositories

GitHub assigns repository ids in roughly chronological order. Scyros either draws ids uniformly at random, with replacement, or in increasing order (--mode linear). Specific flags can be used to set the minimum (with --min) and maximum (with --max) id Scyros queries, as well as the number of ids to query. Due to the nature of the REST API, ids are queried by contiguous chunks of 100. In this tutorial, we will sample 2000 repository ids at random from projects created between the creation of GitHub and 5 Jan 2026 (default max id). To execute this step, run the following command: 

scyros ids -t tokens.csv -n 2000 -o ids.csv

The name of the sampled repositories will be stored in an output CSV file (here named ids.csv). This file contains four columns: the id of each repository, its name, whether it is a fork (1) or not (0), and in which request this repository was sampled.

The random seed is fixed (configurable with -s), so running the same command draws the same ids. In addition, if the process is paused or interrupted, it can be resumed by rerunning the command without losing earlier results while not compromising reproducibility.

2. Remove duplicate ids

Because sampling is with replacement, the same repository can be recorded more than once. To remove duplicate ids, run the following subcommand. 

scyros duplicate_ids -i ids.csv -o unique_ids.csv

The result is stored in unique_ids.csv. On a sample of 2000 ids, the probability of running into duplicates is very low.

3. Remove forks

To avoid popular projects being overrepresented, we also remove forks. With Scyros, you can do this with the following command: 

scyros forks -i unique_ids.csv -o ids_without_forks.csv

The result is stored in ids_without_forks.csv. On average, one third of the repositories in the sample are forks, and should therefore be discarded with this operation.

4. Collect metadata

Run the following command to retrieve each repository's metadata. 

scyros metadata -i ids_without_forks.csv -t tokens.csv -o metadata.csv

This metadata includes the primary language of the repository, its size (in kB), its creation and last push dates (timestamps in Unix time), its popularity counts and its licence.

5. Filter from metadata

Many public repositories are empty, not software projects, or tiny projects abandoned shortly after their creation (see Maj et al., The Fault in Our Stars). Studying developed/engineered repositories means we should exclude these. Following their recommendations, Scyros provides a command to filter all the repositories under a given size (-s, in kB), or younger than a given threshold (-a, the age is defined as the number of days between the last push and the creation date). The --non-code flag allows you to filter repositories without a language assigned by GitHub, most often repositories holding only documentation, data or binaries. The same authors show that popularity metrics such as stars bias such studies, and should therefore be avoided. Let us keep only the projects older than 60 days and bigger than 50 kB with a language assigned by GitHub. The filtered dataset is stored in filtered_metadata.csv. 

scyros filter_metadata -i metadata.csv -s 50 -a 60 --non-code -o filtered_metadata.csv

filter_metadata runs locally on metadata.csv and sends no requests, so you can compare different thresholds cheaply. After this phase approximately 10% of the repositories should remain.

6. Query languages and last commit

GitHub's primary language understates multi-language repositories: a Kotlin project may also contain Java. This command records the full language breakdown of each repository, in bytes, together with its latest commit, which pins the version of the code downloaded in the next steps. 

scyros languages -i filtered_metadata.csv -t tokens.csv -o languages.csv

7. Keep repositories in Java and Go

We now need to keep only the repositories that contain code in Java or Go. To do so, we create a JSON config file that specifies the languages we include in our study:

and run the following command to filter the repositories with the specified languages. The output is stored in java_go_repos.csv. 

scyros filter_languages -i languages.csv -l config.json -o java_go_repos.csv

8. Download the code

The next step is to download the code of the repositories we want to study. The command below downloads the repositories at the commit recorded in step 6, and keeps only the files written in Java or Go and that contain a keyword related to concurrency. To specify this, we extend the config.json file created in step 7 with the file extensions we consider for each language, and the keywords that relate to concurrency:

Each language is now paired with a list of file extensions that Scyros will keep after downloading the repositories, and a list of keywords that will be used to filter the files. The top-level keywords (lock and unlock) are matched in every language. Then run: 

scyros download -i java_go_repos.csv -t tokens.csv -k config.json -d repos -p projects.csv -f files.csv

Each repository is downloaded into repos/ at the commit recorded in step 6, so rerunning the study retrieves identical code, provided the repository is still public and its history has not been rewritten. Files outside the configured extensions, and files containing none of the keywords, are then deleted. The output of this command is stored in projects.csv (per-repository statistics) and files.csv (per-file statistics, with the number of keyword matches in a column named after the keyword file). Because this filter also matches comments and string literals, it is deliberately permissive. A manual inspection of a random sample of the matching files helps assess the precision of the filter.

9. Remove duplicate files

Now that we have statistics at the repository level, we focus on files and functions. From this step on, files are treated as a single pool, independent of their repository. As shown by Lopes et al. in their empirical study on code duplication, GitHub contains substantial cross-repository duplication, such as libraries, generated code and code that users forget to gitignore (e.g., node_modules). These files end up being overrepresented in file- and function-level statistics. Scyros provides a command to deduplicate files across repositories. With the flag -s bow (bag of words), two files are duplicates when they contain the same tokens with the same frequencies, regardless of order and whitespace. -s exact requires byte-identical files, and -s overlap also detects near-miss clones that differ by a few statements, at a much higher cost. unique_files.csv (the name is configurable with the -o flag) keeps one representative per group, with a count column giving the group size; duplicates.csv (the name is configurable with the -m flag) maps each file to its representative. Feel free to try different deduplication strategies (although at this scale all three produce similar results). 

scyros duplicate_files -i files.csv -s bow -o unique_files.csv -m duplicates.csv

10. Extract the functions

The goal of our example study is to extract functions from GitHub that use concurrency primitives. To do this last step, Scyros provides a command to parse the files with Tree-sitter, extract their functions, and keep only those whose body contains at least one keyword. In this step, comments and string literals are not considered for keyword matching, so the filter is more precise than the file-level filter in step 8. Each function is written to its own file and a summary CSV file (in this case functions.csv) is produced with metrics for each function. This includes their size, the number of occurrences of the keywords, which programming constructs they contain (loops, conditionals, function calls), etc. A summary CSV file at the file level (function_logs.csv) is also produced, giving the number of functions found and the number kept per file. 

scyros parse -i unique_files.csv -k config.json -o functions.csv -l function_logs.csv
